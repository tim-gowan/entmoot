# Compatibility controls

Current compatibility behavior is owned by `entmoot-engine` and tested in
`package_compatibility`, `joins_soundness` and the opt-in CLI
`program_adapters` suite. Syntax inventory, resolver target modes and actual runtime
behavior are separate results. C++ remains experimental.

Keep consumer evidence fixed when assessing a candidate provider. Written
boundaries and qualified native symbols support a bounded contract assessment;
they do not prove runtime equivalence. Missing exports, partial scope, unavailable
tools and incomplete references cannot establish incompatibility or absence.

Compatibility is the optional Bound/Fits rung. Prefer `entmoot assess overlay`
for inventory presence across publications, and impact with subject
correspondence for same-package revision deltas. When no consumer
`package_api` importer references match a requested provider coordinate, the
receipt includes a loud
`consumer_missing_importer_refs:<ecosystem:name>` limitation alongside
`no_evaluable_package_sites`. Python bind may emit seeking `package_api`
references from package-qualified native call/reference facts; `uv.lock` can
assert `LockedPackageInstance` rows when `.entmoot/lock_bindings.json` is
absent (strengthens Fits only).

Use the [adapter runbook](resolver-adapters.md) for setup
and the [SQLite harness](../../evals/harness/README.md) for repository campaigns.
Historical measurements are bounded observations, not current release gates.
